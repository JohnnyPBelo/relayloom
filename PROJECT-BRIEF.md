# RelayLoom — resilient peer-to-peer social communication

Working name (not trademark-cleared). Owner: JohnnyPBelo. This file records the requested product, not implemented features.

## Original product intent
Build a highly polished, distinctive, accessible cross-platform application for Windows, Android, macOS, iOS and Linux. It combines modern encrypted messenger UX (inspired by the usability, not branding, of WhatsApp/Telegram), a social network, and beautiful personal profile websites built through an easy drag-and-drop editor. Primary use case: communication during natural disasters and infrastructure outages.

All running installations should participate as active packet relay nodes when platform capabilities and user permissions permit. A route can bridge several media between origin and destination, inspired by Reticulum: transport-independent store-and-forward, multiple hops, partition/delay tolerance. No mandatory central service storing user information. Peer devices store and serve content; a reader becomes a seeder, not its author. Authoritative edits must require the owner's signing private key; decryption/read keys must never confer authorship.

## Functional acceptance scope
- Locally generated cryptographic identities, secure key storage, export/recovery, signed updates, encryption, documented key rotation/revocation limits. Use maintained crypto libraries/protocols, not custom primitives. Separate signing authority, reading access and seeding ability.
- 1:1 and group conversations; text, photo, audio/voice and video/file attachments; offline outbox, delivery/expiry state, replies, reactions, search, edit/delete semantics, blocking, reporting/moderation strategy without a central database, notifications where supported.
- Social profiles, follow relationships, posts/feed, comments/reactions, collections, sharing and privacy controls. Explicit capability matrix for every requested social feature; no fake active buttons.
- Content-addressed encrypted chunks; manifests signed by author; verified on receipt and before display; peer retrieval and cache/seed after view; pin/unpin, disk quotas, bandwidth/battery policy, eviction/TTL. Honest availability, deletion and replication semantics.
- Multi-medium routing with transport adapters, priority/fair scheduling (SOS and small messages before bulk video), MTU/fragmentation/reassembly, retransmits, TTL/hop limits/duplicate suppression, corruption detection, replay controls, abuse/rate limits and resource exhaustion protection.
- Use actual transports where possible, initially real socket/IP multi-process transport plus another genuinely different implemented medium/adapter. Evaluate Reticulum/RNS interoperability and licensing rather than calling a custom simulator Reticulum-compatible. Separate real IP, BLE, Wi-Fi Direct, LoRa/serial/external radio and simulation in a truth table. No unsupported promise of arbitrary radios or media on every OS.
- Multi-hop route can enter one supported medium and leave on another. No mandatory central backend/bootstrap/content server; explicit bootstrap/discovery and NAT/relay tradeoffs, no hidden CDN fonts/assets/analytics/runtime services.
- Drag/drop personal-site editor, responsive templates/blocks, excellent typography/spacing and visual composition, preview, save/publish signed site manifest onto the P2P store; render another user's published profile offline from cached content. Sandboxed declarative blocks; no arbitrary remote scripts or HTML execution. Both touch and keyboard alternatives to drag/drop.
- Emergency UI: offline/network health, nearby/known peers, verified vs unverified alert provenance, high contrast, large targets, low-power mode and accessible critical messaging. NEVER label this validated emergency infrastructure or a replacement for emergency services.
- Original cohesive design system with polished light/dark and reduced-motion states, responsive layouts, accessibility/keyboard/screen reader testing, meaningful error/empty/loading/offline states and real screenshots. No claims of objectively 'unprecedented' quality.

## Verification gates
1. Unit/property tests: addressing, identities/signatures, ACL/read vs write authority, chunk verification, parser/fuzz limits, routing/TTL, bounded cache/queues and eviction.
2. Real multi-process integration: A -> B -> C with A and C unable to communicate directly in the fixture, heterogeneous supported adapters across hops, payload integrity and routing evidence. Prove the isolation with positive/negative controls, not just a topology label. Seed takeover: original publisher offline, reader B serves new reader C. Unauthorized edit/decrypt, tamper and replay fail. Restart/persistence recovery, duplicate floods and partial/churn/partition/heal behavior.
3. Deterministic network simulation with fixed seeds + realistic bandwidth, latency, packet loss, asymmetric links, MTU, congestion, storage exhaustion and low-power transitions. Reports must distinguish simulation from real transport/hardware results; controls must fail when routing or crypto checks are intentionally broken.
4. UI end-to-end through real clients: identity creation, two-user messages, attachments, reactions, group/social flows, site editor publish/view and offline recovery. Screenshots/video and accessibility tests; no localhost-only fake pass as P2P capability.
5. Build/CI target matrix for Windows/Linux/macOS/Android/iOS. A cross-compilation is not device testing. On this Linux machine, use permissible native tools/emulators/containers/CI runners available; do not pretend macOS/iOS run in generic Linux containers. iOS signing and real radio/hardware behavior require suitable devices/Apple tooling; mark blocked/unverified honestly. No paid cloud/VM/hardware purchase without approval.
6. Independent security/reliability/design review, fixes and rerun. Reports map each acceptance criterion to exact test invocation/result/artifact or explicit unsupported/blocked status.

## Invariants and practical limits
Delivery requires an actual eventual path. Narrowband links cannot provide broadband video UX; prioritize tiny emergency messages and defer bulk transfers. Mobile background relaying is constrained by OS policy/battery; no evasion of OS security. Replicated data lives on peers, not nowhere; availability depends on seeders, deletion cannot recall copies, and key compromise/recovery has limits. Do not promise perfect anonymity or availability. Encrypt private content at rest/in transit, minimize metadata and make seeding/storage budgets transparent and controllable. Emergency privacy and consent matter even for relay nodes.

At bootstrap host disk free was only about 46 GiB. Check current resources before downloads/builds. Keep at least 15 GiB free, cap simultaneous builds, never delete unrelated files or stop other workloads, avoid downloading multiple large OS images. Use only this project directory/worktrees and project-scoped caches. No root escalation, no service/security-setting changes, no exposure of unauthenticated control ports. Ask for unavoidable external prerequisites instead of bypassing controls.
